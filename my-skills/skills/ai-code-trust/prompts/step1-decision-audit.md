# Step 1: 决策审计 Prompt 模板

请将以下 Prompt 连同待检查的代码一起发送给 AI。

---

## Prompt

你是一位资深的代码架构审查员。我将给你一段由 AI 生成的代码，请你从**设计决策**的角度进行审计，而不是逐行 review。

### 待审查代码

```
[在此粘贴 AI 生成的代码]
```

### 代码背景

- 这段代码的功能是：[简述功能]
- 所属项目/模块：[项目名或模块名]
- 技术栈：[语言/框架/数据库等]

### 请回答以下三个问题

**问题 1：核心设计决策**

请列出这段代码中 3-5 个最关键的设计决策，包括但不限于：
- 数据结构的选型（为什么用这个数据结构而不是其他？）
- 分层/模块划分方式
- 错误处理策略（是抛异常、返回错误码、还是静默处理？）
- 并发/异步模型的选择
- 依赖的外部服务或库

对每个决策，用一句话说明"选了什么"和"为什么合理"。

**问题 2：取舍与替代方案**

对上述每个设计决策，请说明：
- 有哪些合理的替代方案？
- 当前方案相比替代方案的优势和劣势是什么？
- 在什么条件下应该切换到替代方案？

**问题 3：失效条件**

请列出这段代码可能失效的具体场景，至少覆盖以下维度：
- 数据量增长到什么规模会出问题？
- 并发量达到什么级别会出问题？
- 哪些异常输入会导致非预期行为？
- 哪些依赖服务不可用时会导致什么后果？
- 有没有隐式的时序假设或环境假设？

### 输出格式

请用结构化的方式回答，每个问题单独一节。对于风险项，请标注严重程度（高/中/低）。

---

## 如何解读结果

- 如果 AI 对三个问题都能给出清晰、具体、自洽的回答 → **决策逻辑可追溯**，这段代码的设计是经过"思考"的
- 如果 AI 对某些决策说不清为什么这样选 → 这个决策点需要人工复核
- 如果 AI 的回答自相矛盾（比如说选了 A 方案因为性能好，但失效条件里又说性能是瓶颈）→ 这段代码的可信度要打折扣

---

## 粒度适配

### S 级（单接口）
直接使用上述 Prompt，代码背景中填写单个函数/接口的信息即可。

### M 级（功能模块）
分两轮执行：

**第一轮：模块级决策审计**
在"代码背景"中补充以下信息：
- 模块包含的子单元清单（文件/函数列表）
- 子单元之间的调用关系
- 模块对外暴露的接口

在"问题 1"中额外关注：
- 模块的整体分层/分包策略是否合理？
- 子单元之间的职责划分是否清晰？有没有职责重叠或遗漏？
- 模块内部的通信方式（直接调用/事件/回调）是否一致？

**第二轮：关键子单元决策审计**
对核心路径上的子单元（通常 2-3 个），分别执行一次 S 级的决策审计。

### L 级（跨模块）
在 M 级的基础上，第一轮改为**系统级决策审计**，额外关注：
- 服务拆分的边界是否合理？
- 跨服务通信方式的选择（同步 HTTP / 异步消息 / gRPC）
- 数据一致性策略（强一致 / 最终一致 / Saga）
- 各服务的部署和扩缩容策略
