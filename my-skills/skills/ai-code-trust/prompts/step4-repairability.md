# Step 4: 可修复性评估 Prompt 模板

这一步回答一个核心问题：**如果这段代码明天凌晨 3 点出了线上故障，我能在 30 分钟内定位到问题吗？**

---

## Prompt

你是一位经历过无数次线上故障的 SRE 专家。请从**可观测性和可修复性**的角度审查以下代码。

你的评估标准是：一个对这段代码不熟悉的值班工程师，在凌晨 3 点被告警叫醒后，能否在 30 分钟内定位到问题并执行修复或降级。

### 待审查代码

```
[在此粘贴 AI 生成的代码]
```

### 代码背景

- 功能描述：[简述功能]
- 技术栈：[语言/框架]
- 部署方式：[单机/集群/容器/Serverless]
- 监控体系：[如果有的话，说明用了什么监控工具]

### 请按以下五个维度评估

**维度 1：日志覆盖度**

检查以下关键路径是否有日志：
- 请求入口（入参摘要、请求标识）
- 关键分支判断点（走了哪个分支、为什么）
- 外部调用（调了什么服务、耗时多少、返回什么）
- 错误捕获点（完整的错误信息、堆栈、上下文）
- 请求出口（响应摘要、总耗时）

日志质量检查：
- 日志级别是否合理？（不是所有日志都用 info/error）
- 错误日志是否包含足够的上下文？（请求 ID、用户标识、关键参数）
- 日志量是否合理？（不会在高流量下把磁盘打满）
- 是否有 traceId/requestId 串联整个调用链？

**维度 2：错误可追溯性**

- 异常是否被正确捕获和传播？（不是被 catch 后吞掉）
- 错误信息是否有意义？（不是只打印 "error" 或 "something went wrong"）
- 是否区分了业务错误和系统错误？
- 错误码是否有文档或注释说明含义？
- 嵌套调用中的错误是否保留了原始堆栈？

**维度 3：监控可观测性**

- 是否有关键业务指标的埋点？（成功率、耗时分布、错误率）
- 是否有资源使用指标？（连接池使用率、队列长度、内存使用）
- 是否有告警规则的建议？（什么指标超过什么阈值应该告警）
- 是否有 dashboard 可以快速看到整体健康状态？

**维度 4：降级预案**

- 依赖服务不可用时是否有降级策略？（返回缓存数据、返回默认值、跳过非核心功能）
- 是否有功能开关可以快速关闭某个功能？
- 是否有限流/熔断机制？
- 降级后是否有恢复机制？
- 降级策略是否经过测试？

**维度 5：代码可读性（面向故障排查）**

- 核心逻辑是否有注释说明 **why**（不是 what）？
- 变量命名是否自解释？
- 复杂的业务规则是否有文档或注释？
- 魔法数字是否有常量定义和说明？
- 代码结构是否便于快速定位到出问题的模块？

### 输出格式

对每个维度，请给出：

```
### 维度 [编号]：[维度名称]
- 评级：🟢 充分 / 🟡 部分缺失 / 🔴 严重缺失
- 现状描述：[当前代码在这个维度做得怎么样]
- 缺失项：[具体缺少什么]
- 改进建议：[具体应该怎么补]
- 优先级：[高/中/低——基于"凌晨3点能否快速定位"的标准]
```

最后请给出一个综合评估：
- 当前可修复性等级：🟢/🟡/🔴
- 最需要优先补充的 1-3 项改进
- 预估补充这些改进需要的工作量

---

## 如何解读结果

- **五个维度全部 🟢** → 可修复性优秀，出了问题能快速定位和恢复
- **日志和错误追溯为 🟢，其他有 🟡** → 基本可修复，建议逐步补全
- **日志或错误追溯为 🔴** → 可修复性严重不足，上线前必须补全关键路径的日志和错误处理
- **降级预案为 🔴** → 如果是核心服务，必须补充降级策略；如果是非核心功能，可以标记为已知风险

## 快速补全清单

如果评估结果不理想，以下是按优先级排序的补全建议：

1. **最高优先级**：给所有 catch 块加上有意义的错误日志（包含上下文）
2. **高优先级**：给请求入口和出口加上日志（含 requestId）
3. **中优先级**：给外部调用加上超时设置和错误处理
4. **中优先级**：给核心业务逻辑加上 why 注释
5. **低优先级**：补充监控埋点和告警规则
6. **低优先级**：设计和实现降级预案

---

## 粒度适配

### S 级（单接口）
直接使用上述 Prompt，评估单个函数/接口的五个维度即可。

### M 级（功能模块）
在五个维度之外，额外评估**模块级可修复性**：

**维度 6：模块级链路追踪**
- 一个请求经过模块内多个函数时，能否通过日志串联完整调用链？
- 模块内部的错误，在模块对外的接口上是否有清晰的体现？（而不是返回一个笼统的 500）
- 模块整体是否有健康检查接口？
- 模块是否可以作为一个整体被降级/关闭？

### L 级（跨模块）
在 M 级的基础上，额外评估**系统级可修复性**：

**维度 7：全链路可观测性**
- 跨服务的请求是否有统一的 traceId 贯穿？
- 是否有全链路的调用拓扑图（如 Jaeger、Zipkin、CAT）？
- 某个服务出问题时，能否快速判断影响范围（哪些上游受影响）？
- 是否有全局的 dashboard 展示各服务的健康状态和依赖关系？

**维度 8：系统级降级与恢复**
- 是否有全局的降级预案（而不仅仅是单个服务的降级）？
- 降级的粒度是否合理？（能否只降级出问题的功能，而不是整个系统）
- 故障恢复后，是否有数据补偿/对账机制？
- 是否有定期的故障演练？
