# AI Code Trust — AI 产出代码信任建立工具

## 核心理念

信任的本质不是"确认没问题"，而是"知道它在什么范围内可靠，超出范围有预案"。

这个 Skill 解决的是一个真实痛点：AI 写的代码看起来对、测试也过了，但你心里慌——因为你不知道"没出问题"到底是"真的没问题"还是"还没碰到那个会出问题的条件"。

慌张的本质是三层恐惧叠加：看不懂决策逻辑、不知道测试够不够、出了问题不确定能不能修。这个 Skill 通过结构化的四步检查，在不要求你完全看懂每一行代码的前提下，建立可校准的信心。

## Step 0：粒度判断（Scope Triage）

在开始四步检查之前，先判断待检查代码的粒度。不同粒度决定了检查深度、关注重点和输出形式。

### 三种粒度

**S 级：单函数/单接口**
- 典型场景：AI 帮我写了一个接口、一个工具函数、一段数据处理逻辑
- 代码量：通常 1 个文件，几十到几百行
- 判断依据：用户给的是一段连续的代码，或指向单个文件/函数
- 检查策略：四步全走，每步聚焦代码本身，不需要考虑模块间交互
- 预计耗时：10-15 分钟

**M 级：功能模块**
- 典型场景：AI 帮我写了整个用户认证模块（注册+登录+Token刷新+权限校验）、一个完整的 CRUD 模块
- 代码量：多个文件，几百到几千行
- 判断依据：涉及多个文件/函数，它们之间有调用关系或共享状态
- 检查策略：先拆解为子单元，每个子单元做 S 级检查，最后额外做一轮**模块内交互检查**
- 预计耗时：30-60 分钟

**L 级：跨模块/系统级**
- 典型场景：AI 帮我写了一个完整的订单流程（下单→支付→库存→通知）、一个涉及前后端的完整功能
- 代码量：跨多个服务/模块，可能上万行
- 判断依据：涉及多个独立模块之间的协作，有跨服务调用、消息传递、分布式事务
- 检查策略：每个模块做 M 级检查，最后额外做一轮**跨模块交互检查**（数据流、事务一致性、失败传播）
- 预计耗时：1-2 小时

### 粒度判断规则

当用户提供代码时，按以下顺序判断：

1. 代码是否跨越了多个独立服务或模块边界？→ 是：L 级
2. 代码是否涉及多个文件，且文件之间有调用关系？→ 是：M 级
3. 以上都不是 → S 级

如果不确定，**默认按 M 级处理**——宁可多检查一层交互，不要漏掉模块间的问题。

### 各粒度的检查流程差异

| 维度 | S 级（单接口） | M 级（功能模块） | L 级（跨模块） |
|------|----------------|------------------|----------------|
| Step 1 决策审计 | 审计单个函数的设计决策 | 先审计模块的整体架构决策，再审计关键子单元 | 审计系统级的架构决策（服务拆分、通信方式、数据一致性策略） |
| Step 2 脆弱性扫描 | 扫描代码本身的脆弱点 | 额外扫描模块内部的接口契约和状态共享 | 额外扫描跨服务的数据流、事务边界、失败传播链 |
| Step 3 边界爆破 | 对单个接口构造恶意输入 | 额外构造模块内部的交互异常（A 调 B 时 B 返回异常） | 额外构造跨服务的级联故障场景 |
| Step 4 可修复性 | 评估单个接口的可观测性 | 额外评估模块级的链路追踪和整体降级 | 额外评估跨服务的全链路追踪、分布式故障定位能力 |
| 输出格式 | 单份信任报告 | 模块总报告 + 关键子单元附录 | 系统总报告 + 各模块摘要 + 交互风险专项 |

### M 级额外检查项：模块内交互

当粒度为 M 级时，在四步检查之外，额外检查以下内容：

1. **接口契约**：模块内各函数/类之间的调用，入参和返回值的约定是否一致？有没有"A 函数以为 B 返回数组，但 B 实际返回 null"的情况？
2. **状态共享**：模块内是否有共享的可变状态（全局变量、单例、缓存）？多个函数同时读写时是否安全？
3. **错误传播**：A 调用 B，B 抛出异常时，A 是否正确处理了？错误信息是否在传播过程中丢失？
4. **初始化顺序**：模块内各组件的初始化是否有依赖顺序？顺序错了会怎样？

### L 级额外检查项：跨模块交互

当粒度为 L 级时，在 M 级检查之外，额外检查以下内容：

1. **数据一致性**：跨服务操作是否有事务保障？部分成功时如何回滚？最终一致性的窗口期是否可接受？
2. **失败传播链**：服务 A 调用服务 B 失败时，错误如何传播到上游？是否会导致级联故障？
3. **超时与重试**：跨服务调用的超时设置是否合理？重试是否幂等？重试风暴是否有防护？
4. **数据流完整性**：数据从入口到出口经过的每个服务，格式转换是否正确？有没有字段丢失或类型变化？
5. **部署顺序**：多个服务需要同时上线时，是否有部署顺序依赖？能否灰度发布？

## 四步信任检查流程

### Step 1：决策审计（Decision Audit）

目标：理解 AI 的设计决策，而不是每一行实现细节。

对 AI 生成的代码，提出以下三个问题：

1. **核心设计决策**：这段代码做了哪些关键的设计选择？（数据结构选型、分层方式、错误处理策略、并发模型等）
2. **取舍与替代方案**：每个决策有什么替代方案？为什么选了当前方案而不是其他？
3. **失效条件**：在什么条件下这段代码会出问题？（数据量增长、并发场景、异常输入、依赖服务不可用等）

使用 `prompts/step1-decision-audit.md` 中的 Prompt 模板，将代码喂给 AI 获取回答。

**判断标准**：
- 如果 AI 能清晰回答这三个问题 → 决策逻辑可追溯，信任 +1
- 如果 AI 回答含糊或自相矛盾 → 这段代码的可信度要打折扣，标记为黄色

### Step 2：脆弱性扫描（Vulnerability Scan）

目标：用独立的第二视角找出设计层面的脆弱假设。

关键原则：**用不同的模型或不同的 session 来审查**，避免自我确认偏差。

审查重点（按优先级排序）：

1. **边界条件处理**：空值、零值、负数、超大数据、空集合
2. **异常路径**：网络超时、依赖服务不可用、数据库连接失败
3. **并发安全**：竞态条件、死锁风险、数据一致性
4. **安全漏洞**：SQL 注入、XSS、硬编码密钥、未鉴权接口
5. **隐式假设**：代码中没有显式检查但默认成立的前提条件
6. **资源泄漏**：未关闭的连接、未释放的锁、内存泄漏

使用 `prompts/step2-vulnerability-scan.md` 中的 Prompt 模板。

**判断标准**：
- 发现 0 个高危问题 → 绿色
- 发现 1-2 个中危问题且有明确修复方案 → 黄色
- 发现高危问题（安全漏洞、数据一致性风险）→ 红色，必须修复后重新检查

### Step 3：边界爆破测试（Boundary Blast Test）

目标：构造"故意搞破坏"的测试用例，验证异常路径。

让 AI 生成一组恶意测试用例，覆盖以下场景：

1. **空值/零值攻击**：所有可选参数传 null/undefined/空字符串/0
2. **超大数据**：超长字符串、超大数组、超大数字
3. **非法格式**：类型错误、格式畸形、编码异常
4. **并发压力**：同时发起多个相同请求、快速重复提交
5. **超时场景**：模拟依赖服务响应极慢
6. **状态异常**：在不该调用的时机调用（未初始化、已销毁、重复调用）

使用 `prompts/step3-boundary-blast.md` 中的 Prompt 模板。

**判断标准**：
- 所有恶意测试通过（优雅降级或正确拒绝）→ 绿色
- 部分测试暴露了未处理的异常但不影响核心功能 → 黄色
- 测试导致崩溃、数据损坏或安全问题 → 红色

### Step 4：可修复性评估（Repairability Assessment）

目标：确认出了问题你能定位和修复。

回答一个核心问题：**如果这段代码明天凌晨 3 点出了线上故障，我能在 30 分钟内定位到问题吗？**

检查以下几项：

1. **日志覆盖**：关键路径是否有足够的日志？错误日志是否包含上下文信息（请求参数、用户标识、时间戳）？
2. **错误可追溯**：异常是否被正确捕获和传播？错误信息是否有意义（而不是吞掉异常或只打印 "error"）？
3. **监控可观测**：是否有关键指标的埋点（接口耗时、错误率、关键业务指标）？
4. **降级预案**：依赖服务不可用时是否有降级策略？是否有开关可以快速关闭某个功能？
5. **代码可读性**：核心逻辑是否有注释说明 why（不是 what）？变量命名是否自解释？

使用 `prompts/step4-repairability.md` 中的 Prompt 模板。

**判断标准**：
- 日志充分、错误可追溯、有降级预案 → 绿色
- 部分缺失但可以快速补上 → 黄色
- 关键路径无日志、异常被吞、无降级 → 红色，必须补全后才能上线

## 综合信任等级判定规则

- **🟢 可信**：四步检查全部为绿色，或仅有低优先级的黄色项
- **🟡 有条件可信**：存在黄色项但无红色项，已知风险可接受且有应对方案
- **🔴 需要修复**：存在任何红色项，必须修复后重新执行检查

## 使用方式

### 执行流程

1. **Step 0 粒度判断**：根据用户提供的代码范围，判断是 S/M/L 哪个级别
2. **告知用户粒度和预计耗时**：让用户知道接下来会做什么、大概需要多久
3. **按粒度执行四步检查**：S 级直接走四步；M 级先拆解子单元再逐个检查；L 级先拆解模块再逐个检查
4. **执行额外检查**：M 级做模块内交互检查，L 级做跨模块交互检查
5. **输出对应粒度的信任报告**

### 快速模式 vs 完整模式

用户可以选择检查深度：

- **快速模式**（"快速看一下"、"简单检查"）：只执行 Step 1 + Step 2，输出精简报告。适合开发阶段的快速反馈。
- **完整模式**（"准备上线"、"完整验收"、"代码信任检查"）：四步全部执行 + 粒度对应的额外检查，输出完整报告。适合上线前的正式验收。

如果用户没有明确说明，默认使用**完整模式**。

### 关键原则

对于 Step 2（脆弱性扫描），强烈建议使用不同的模型或新的对话 session 来执行，以避免自我确认偏差。如果条件不允许，至少要在 Prompt 中明确要求 AI 扮演"恶意审查者"角色。

对于 M 级和 L 级，不需要对每个子单元都做完整的四步检查——优先检查核心路径和高风险单元，对低风险的辅助单元可以只做 Step 1 + Step 2。

## 被引用接口（供其他 Skill 调用）

本 Skill 既可以独立使用，也可以作为其他 CR/测试 Skill 工作流中的一个环节被引用。

### 触发条件

当调用方的 CR 流程检测到以下任一条件时，应引用本 Skill：

1. **代码由 AI 生成或大量 AI 辅助**：commit message 包含 AI 工具标识（Copilot、Cursor、Claude 等），或用户明确说明代码是 AI 写的
2. **代码变更量大且缺少人工审查痕迹**：单次提交新增 > 200 行，且无逐行 review 记录
3. **用户主动要求**：用户说"帮我做信任检查"、"AI 代码验收"等

### 调用方式

调用方读取本 Skill 的 SKILL.md，按以下约定执行：

**输入**：调用方需提供以下信息：
- 待检查的代码（文件路径或代码片段）
- 代码背景（功能描述、技术栈、部署环境）
- 粒度提示（可选，调用方可根据 diff 范围预判 S/M/L）

**执行模式**：
- **嵌入模式（推荐）**：调用方在自己的流程中执行 ai-code-trust 的 Step 1（决策审计）+ Step 2（脆弱性扫描），将结果嵌入自己的报告。适合不想让整体流程太长的场景。
- **完整模式**：调用方委托 ai-code-trust 执行全部四步，将信任报告作为附录附在自己的报告后面。适合上线前的正式验收。

**输出约定**：
- 信任报告作为调用方报告的一个独立章节，标题为 `🔍 AI 代码信任检查`
- 信任等级（🟢/🟡/🔴）纳入调用方的最终结论判定：
  - 🔴 信任等级 → 等同于调用方的 P1（强烈建议修复）
  - 🟡 信任等级 → 等同于调用方的 P2（应修复）
  - 🟢 信任等级 → 不影响调用方结论

### 降级策略

如果本 Skill 未安装（路径不存在），调用方应输出：
```
⚠️ ai-code-trust Skill 未安装，跳过 AI 代码信任检查。
建议安装以获得 AI 产出代码的信任校准能力。
```
